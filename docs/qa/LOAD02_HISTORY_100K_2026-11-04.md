## Important acceptance boundaries

This test is a deterministic **SQLite+StoreService cursor correctness benchmark** only. It is not a 100,000-order live HTTP test, cashier UI search benchmark, 100,000 PAID sales, 8 physical phones, Windows host, or store Wi-Fi performance measurement. CI p95 is informational and not a commercial LAN SLO pass. Separate field tests must measure ≥100k cashier search p95 ≤300ms and normal LAN commit p95 ≤400ms as defined in `docs/qa/ACCEPTANCE.md`.

The SQL plan and timings must be inspected. If the query shows a full scan or unacceptable tail latency, record a performance finding; do not report commercial LOAD-02 fully PASS without realistic target hardware.

Observed `EXPLAIN QUERY PLAN`:

```text
SCAN orders USING INDEX idx_orders_created
USE TEMP B-TREE FOR LAST TERM OF ORDER BY
```

**Finding:** SQLite uses an existing `created_at` index but still builds a temporary B-tree for the `id` tie-breaker. This does not invalidate the measured CI correctness or speed; however it indicates a potential opportunity for an additive composite cursor index, especially for a Windows cashier with lower memory and more tie timestamps. Recommend a **separate backend performance change** with evidence before and after, including `(created_at DESC, id DESC)` and a scoped index `(created_by, created_at DESC, id DESC)` if query planner confirms benefit. Do not alter DB schema as part of this QA-only PR.

**Release verdict:** this synthetic backend `LOAD-02` subtest is **PASS**, but the full acceptance criterion (100k historical rows with cashier search/UI p95 <=300ms on the actual Windows POS, plus LAN load p95) remains **NOT VERIFIED / Commercial NO-GO**.
